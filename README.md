# rag-temario

Ask a question about 1,280 pages of Spanish statistical regulation and get an answer
with the document and page it came from — plus the harness that measures whether the
retrieval behind it actually works.

The corpus is an official syllabus of Spanish public statistics: 30 PDFs, ~778k tokens,
dense technical Spanish. I chose it
for what most corpora lack: real exam questions, written by someone other than me, to
grade the retrieval against.

**The part worth your time is [evaluation](#evaluation).** Building a RAG pipeline is a
weekend. Knowing whether it retrieves the right thing is the part most of them skip.

---

## The pipeline

| Step | Choice | Why |
|---|---|---|
| Ingest | `pypdf`, page-anchored | Every chunk keeps its document and page so the answer can cite something checkable |
| Clean | positional header/footer stripping | Repeated lines at the page edges, detected statistically rather than hard-coded per publisher |
| Chunk | token windows with overlap, configurable | Chunk size is an experimental parameter here, not a number copied from a tutorial |
| Embed | `gemini-embedding-2` at 768 dimensions; query and passage told apart by an instruction in the text | Asymmetric retrieval: a one-line question has to match an 800-token passage. Model and dimension are part of the cache key, so vectors from different configurations cannot mix |
| Store | pgvector (HNSW, cosine) + an exact NumPy store | The exact store is the ground truth the approximate index is measured against |
| Retrieve | dense, BM25, or RRF hybrid | BM25 is a serious competitor on this corpus and refusing to measure it is how you end up paying an API to lose to `grep` |
| Re-rank | one Gemini call scoring 20 candidates | Retrieve 20, keep 5. Similarity is not relevance |
| Answer | structured output, citations required, refusal allowed | `answered=false` is a valid response |

`gemini-embedding-2` takes no `task_type`: the task is written into the text, in the format
[Google documents](https://ai.google.dev/gemini-api/docs/embeddings#task-types-embeddings-2)
(`task: search result | query: …` for a question, `title: none | text: …` for a passage).
`gemini-embedding-001` is still supported and gets `task_type` instead — set
`RAG_EMBED_MODEL`; the size is `RAG_EMBED_DIM`.

Orchestration is exposed twice on purpose: a direct path used by the evaluation harness,
and a LangChain `BaseRetriever` + LCEL chain (`rag chain`) for composing with that
ecosystem. Measuring a system means controlling every step of it; a framework in the
middle is one more place for a default to move the numbers.

## Evaluation

### The labels are not mine

The standard advice is to hand-write ~50 questions. That produces an eval set shaped by
the phrasing of the person building the system — the one bias an eval set must not have.

This corpus ships with something better: **the real exams**, published by the examining body, whose
questions sit under headings that name the syllabus area they belong to. The heading is
the label, written by the examiner rather than by the engineer being graded.

```
98 questions, de-duplicated from 7 official exams (186 raw)
  86 labelled with a syllabus area  →  estadistica 40 · economia 19 · demografia 13 · muestreo 7 · informatica 7
  12 with no supporting document at all
```

Those last 12 are the gift. One exam block — *Derecho Público y Organización del Estado* —
has no syllabus in this corpus. A retriever always returns its top k, so it never says
"I don't know"; these 12 measure whether the system can.

### Measured against what

A recall number without a baseline is decoration. 46% of this corpus is `estadistica`, so
a retriever returning **random** chunks already scores recall@5 ≈ 0.75. Every result is
reported next to:

- the analytic random baseline, `1 - Π (N-Nₐ-i)/(N-i)`, averaged over the eval set's area mix,
- the majority-area baseline (0.465),
- BM25, which is not a formality.

Metrics: **recall@k** (can generation possibly be right), **MRR** (recall@20 looks healthy
when every correct chunk sits at rank 18 — re-ranking then has to rescue it),
**precision@k** (how much of the context window is wasted), and **out-of-corpus AUC**: the
rank-based AUC of the top-1 similarity score as a detector for the 12 unanswerable
questions. It needs no LLM call, so it is free and not confounded by the generator.

### Results

Generated by `make eval` (`make eval-offline` for the hash embedder). Each embedder writes
its own table — [`eval/RESULTS-gemini-embedding-2-768.md`](eval/RESULTS-gemini-embedding-2-768.md)
and [`eval/RESULTS-hash-256.md`](eval/RESULTS-hash-256.md) — so one run cannot overwrite the
other, and a run limited to some configurations or questions gets a `-partial` suffix. The
`s` column in those files is that run's wall-clock time; with a warm embedding cache it
measures retrieval only.

#### The offline floor

The table below is the **offline floor**: a deterministic hashing embedder with no
semantics at all, included so every other row has something to beat, and so the whole
pipeline can be exercised with no API key and no bill.

| configuration | chunks | R@1 | random R@1 | R@5 | random R@5 | MRR | out-of-corpus AUC |
|---|---|---|---|---|---|---|---|
| `hash-256_400-50_dense` | 2266 | 0.593 | 0.282 | 0.907 | 0.747 | 0.729 | 0.337 |
| `hash-256_800-100_dense` | 1138 | 0.628 | 0.282 | 0.849 | 0.748 | 0.737 | 0.328 |
| `hash-256_1200-150_dense` | 764 | 0.686 | 0.281 | 0.884 | 0.748 | 0.768 | 0.348 |
| `hash-256_page_dense` | 1279 | 0.651 | 0.299 | 0.872 | 0.742 | 0.736 | 0.336 |
| `hash-256_800-100_bm25` | 1138 | **0.930** | 0.282 | **0.988** | 0.748 | **0.956** | 0.696 |
| `hash-256_800-100_hybrid` | 1138 | 0.814 | 0.282 | 0.977 | 0.748 | 0.886 | **0.776** |

Read that bottom pair before the top four. **BM25 — a 1994 lexical algorithm with no
embeddings, no API and no vector database — retrieves the right syllabus area at rank 1
for 93% of real exam questions.** Any dense configuration has to beat that to justify its
own existence. The hybrid row looked like evidence that fusing the two is what separates
in-corpus from out-of-corpus questions (AUC 0.78 vs 0.70); with a real model that did not
hold, as the next section shows.

#### A real embedding model

The same sweep with `gemini-embedding-2` at 768 dimensions, run on 8 October 2026: the same
98 questions (86 with a syllabus area), the same chunkings, exact cosine search in the local
store. The BM25 row uses no embeddings and reproduces the one above digit for digit.

| configuration | chunks | R@1 | random R@1 | R@5 | random R@5 | MRR | out-of-corpus AUC |
|---|---|---|---|---|---|---|---|
| `gemini-embedding-2-768_400-50_dense` | 2266 | 0.942 | 0.282 | 1.000 | 0.747 | 0.969 | 0.974 |
| `gemini-embedding-2-768_800-100_dense` | 1138 | 0.953 | 0.282 | 1.000 | 0.748 | 0.977 | 0.979 |
| `gemini-embedding-2-768_1200-150_dense` | 764 | 0.965 | 0.281 | 1.000 | 0.748 | 0.981 | 0.958 |
| `gemini-embedding-2-768_page_dense` | 1279 | 0.977 | 0.299 | 1.000 | 0.742 | 0.988 | **0.988** |
| `gemini-embedding-2-768_800-100_bm25` | 1138 | 0.930 | 0.282 | 0.988 | 0.748 | 0.956 | 0.696 |
| `gemini-embedding-2-768_800-100_hybrid` | 1138 | **0.988** | 0.282 | 1.000 | 0.748 | **0.994** | 0.785 |

R@5 is 1.000 in five of the six rows, so nothing is in bold there.

**Dense beats BM25: narrowly on where the right area is, widely on whether to answer.** At
rank 1 the four dense configurations land the right area for 81–84 of the 86 in-corpus
questions; BM25 gets 80. At rank 5 every dense row gets all 86 and BM25 misses one. The wide
gap is the out-of-corpus AUC: the top-1 cosine separates the 12 unanswerable questions from
the rest at 0.96–0.99, BM25's score at 0.70. That score is what a refusal threshold would be
set on.

**Hybrid is the best ranker and a poor abstainer.** RRF has the best R@1 and MRR of the
table (85 of 86, 0.994) but an AUC of 0.79, against 0.98 for the dense row it fuses. RRF
scores are functions of rank, not of similarity, so the fused top-1 score no longer carries
what the dense AUC is made of; that is my reading, I did not isolate it. It reverses what the
offline table suggested: with a real model it is the dense similarity that separates
in-corpus from out-of-corpus questions, and fusing discards it. A pipeline that wants both
would have to read the dense score before the fusion.

**The table has run out of resolution.** R@5 is 1.000 for every dense row, so it can no
longer tell chunk sizes apart; the R@1 spread from 400-token windows to whole pages is 81 to
84 questions of 86, and the AUC rests on 12 negatives. That is a few questions, not a
trend, and I would not choose a chunk size from it. A five-area label was always going to
run out of headroom once the embedder was good (see Limitations); document-level labels are
the next thing worth building. The 12 negatives are also the easy case — public law next to
a statistics syllabus — so how the score behaves on a question that is *almost* in the
corpus is not measured.

**Model comparison, one configuration.** `800-100` dense with `gemini-embedding-001` at 768
dimensions (`task_type`, vectors normalised by hand): R@1 0.965 (83 of 86), R@5 1.000, MRR
0.983, AUC 0.986 ([`eval/RESULTS-gemini-embedding-001-768-partial.md`](eval/RESULTS-gemini-embedding-001-768-partial.md)),
against 0.953 (82 of 86), 1.000, 0.977, 0.979 for `gemini-embedding-2`. One question apart:
this evaluation cannot tell them apart. The default is the newer model because the older one
is deprecated (shutdown 14 May 2028), not because of this table.

**Cost.** The sweep embeds 5,447 chunks — about 3.5 M tokens by the cl100k proxy, not
Google's own count — in 134 requests of up to 50 texts. It took about three minutes, 7 of the
requests were retried after a 429, and a second run was served entirely from the cache with
no request at all. At Google's paid price for text input ($0.20 per million tokens) that is
about US$0.70; on the free tier, nothing.

## What broke

**The first version defaulted to an embedding model Google had already shut down.**
`text-embedding-004` was retired on 14 January 2026 ([deprecations
page](https://ai.google.dev/gemini-api/docs/deprecations)); the default in the code, in
`.env.example` and in the dimension table all still named it. Nothing caught it, because the
only path ever run end to end was the offline hash embedder, which needs no model: the
results table had its offline half and nothing else. What changed: the default is
`gemini-embedding-2` at an explicit 768 dimensions (`RAG_EMBED_DIM`, sent as
`output_dimensionality`); model and dimension are part of every cache key and of the index
name, so a vector from one configuration cannot be served for another; the cache is written
after every batch instead of at the end of the call; and rate limits are waited out — the
API's own retry delay when it gives one, otherwise doubling up to a minute — instead of five
attempts in 15 seconds. The new model also has no `task_type` (the task is a prefix in the
text now) and, per the docs, folds a bare list of strings into a single vector, so every
text goes in its own `Content` and a response with the wrong number of vectors is an error.
That last point I took from the docs and the SDK source; I did not send the old call shape
to watch it fail.

**The embedding cache could not fill.** `EmbeddingCache` defines `__len__`, so an empty one
is falsy, and the write was guarded by `if self._cache:` — false until something has been
written, so nothing ever was. A re-run would have re-embedded, and re-billed, the whole
corpus. The tests for per-batch writes found it before any API call did; the guard is
`is not None` now, and a test named after the failure asserts that a fresh cache gets
written. After the first real sweep, the second one made zero requests.

**My own cleaner deleted the data.** The header/footer stripper masks digits before
comparing lines, so `Página 3 de 8` and `Página 4 de 8` collapse into one repeated line.
It also collapsed `Pregunta 1.`, `Pregunta 2.`, … — and deleted every question from the
exams it was cleaning. The eval set built cleanly and came out with **zero questions**, a
failure that is invisible unless you look, because an empty eval set reports perfect
scores on nothing. Fix: boilerplate is *positional* — a header is a header because it sits
at the edge of the page. There is a regression test named after this.

**Then it deleted short pages.** With the positional rule, a 4-line page is entirely
"edge", so every line qualified for removal. Caught by a unit test before it reached the
corpus. The band now shrinks so the middle of a page is never a removal candidate.

**The cache did not know the code had changed.** Parsing 1,280 pages takes 70 s, so it is
cached and keyed by the PDFs' paths, sizes and mtimes. Change the *parser* and the inputs
are identical — you keep serving results from the old logic. The fingerprint now includes
a parser version.

**A retrieval-mode flag could have dropped a production index.** BM25 needs no vectors, so
that path called `store.reset(1)`. Against pgvector, `reset` re-creates the table for the
declared dimension: running one lexical configuration would have dropped the real 768-dim
index. The lexical path now never touches the vector store.

**PDF kerning splits words** — `envejecida` extracts as `env ejecida`. Dense retrieval
shrugs; BM25 cannot match a term that is not there. Before writing a fixer I measured it:
**0.30% of alphabetic tokens**, and the overwhelming majority are function words
(`e`+`n` → `en`) that no retriever depends on. So the repair is deliberately narrow —
content words of 6+ characters, merged only when the corpus itself attests the merged form
more often than either fragment. The measurement is the deliverable; the fixer is small on
purpose.

## Run it

```bash
uv sync                       # Python 3.12+
cp .env.example .env          # add GEMINI_API_KEY (free tier is enough)

make eval-offline             # full sweep, no API key, no cost
make eval                     # full sweep with the real embedding model
make eval-set                 # rebuild the labelled eval set from the exams
make index                    # chunk + embed + index
make ask Q="¿qué es un estimador insesgado?"
make check                    # ruff + pytest
```

`make` is a convenience, not a requirement: every target is one line over the CLI, which
`uv sync` installs as `rag`. Without it:

```bash
uv run rag eval --offline     # make eval-offline
uv run rag eval               # make eval
uv run rag build-eval-set     # make eval-set
uv run rag index              # make index
uv run rag ask "¿qué es un estimador insesgado?"
uv run ruff check src tests && uv run pytest -q    # make check
```

(`.venv/bin/rag …` is the same command after `uv sync`.) The embedding model and its size
come from `.env` (`RAG_EMBED_MODEL`, `RAG_EMBED_DIM`). Vectors are cached in
`data/cache/embeddings.sqlite` after every batch, keyed by model, dimension, task and text:
switching model never mixes vectors, re-running a sweep costs nothing, and one that was
interrupted — by a quota, by the network, by Ctrl-C — resumes where it stopped.

The corpus PDFs are not in this repo — they are publicly available from the examining body. Point
`RAG_CORPUS_DIR` and `RAG_EXAMS_DIR` at your own copy (by default `corpus/` and `exams/` in
the repo root, both git-ignored); any folder of PDFs with one sub-folder per area works.

## Limitations

- **The labels are coarse.** Five areas, with a skewed prior — hence the baselines next to
  every number. A document-level ground truth (30 classes) would discriminate far better
  and is the obvious next increment.
- **Formulas do not survive extraction.** These are statistics PDFs; `pypdf` returns
  LaTeX-ish rubble for equations. Questions that hinge on a formula are being retrieved on
  their prose alone.
- **No answer-quality metric.** Everything here measures *retrieval*. Whether the
  generated answer is correct given correct passages is not scored, only whether it cites
  and whether it refuses.
- **`cl100k_base` is a proxy tokenizer**, not the embedding model's own. It is
  deterministic, offline and free, which matters more for comparing configurations than
  matching the provider's count exactly.
- **One embedding setup, not a tuned one.** Queries use Google's generic `search result`
  instruction (the documented `question answering` variant was not tried); passages go in as
  `title: none | text: …`, so every retriever sees the same text and the document title does
  not hand the embedder the syllabus area being scored; and the vectors are 768 of the 3072
  dimensions available. None of these was swept.
- **Only retrieval was run against the real API.** Re-ranking and answering call
  `gemini-2.5-flash`, which Google now serves only to accounts that already used it and no
  longer recommends for new projects ([deprecations
  page](https://ai.google.dev/gemini-api/docs/deprecations), 8 October 2026). That default
  may need changing, and I did not run either step.

## Not in scope

run record per configuration to `data/runs/*.json`, so it is a matter of logging those
fields rather than restructuring anything.
